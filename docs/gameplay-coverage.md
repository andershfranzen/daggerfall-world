# Gameplay coverage

This document shows which classic gameplay is verified by `test/rpg-world-integration.test.mjs` and which is not. Each case uses two independent characters in one shared world. Each case checks state and ownership: who holds an item, who paid, and what was saved to SQLite. It does not stop at checking that a menu opened.

```
npm test                                                  # whole suite
node --test test/rpg-world-integration.test.mjs           # this matrix only (several minutes with installed assets)
RPG_INTEGRATION_STRICT=1 node --test test/rpg-world-integration.test.mjs   # gaps fail; a missing ARENA2 fails
```

## Evidence layers

| Layer | What is real | What is substituted |
|---|---|---|
| **fixture** | `server/rpg/runtime.js` and every feature in the `server/rpg/features.js` manifest, a SQLite file through `server/db.js`, account-backed rows (`createForAccount`), and cold restarts on the same file | In-process clients replace sockets. Messages still pass through a JSON round trip. The join, leave, and tick glue in `test/support/rpg-session.mjs` follows `docs/gameplay-protocol.md`. |
| **live** | `server/game.js` and `server/accounts.js` on loopback, two accounts registered through `/api/register`, cookie-authenticated WebSockets, `{type:'action',seq}` and `actionResult`, server restart on the same database files | No browser and no game assets. The features come from the manifest. |
| **asset** | The operator's own ARENA2 (gitignored `gamedata/DaggerfallGameFiles/arena2`) is passed as `ctx.dataPath` / `arena2Dir` to the full production manifest, in both the fixture and a live server. That gives real collision geometry, NPC rosters, original QBN/QRC quests and travel data. | The quest catalogue is narrowed to one original quest through `install(ctx, {catalog})`, the same approach the quest owner's tests use, so that the offer is deterministic. These cases are skipped when `gamedata/` is absent, and they fail under strict mode. The no-asset cases above still run on the open plane with the built-in catalogues. |
| **browser** | Not covered by this file. See [Browser journal and menu layout](#browser-journal-and-menu-layout) below for the unit regression and the live browser audit. | Screens need browser captures with real player-supplied game files. Keep those captures out of the repository. |

The tests do not wait on the wall clock. The fixture uses a manual clock. Live waits resolve when a message arrives, and their timeouts only limit how long a failure takes. Feature randomness is seeded at install time, and combat uses a pinned seed (`FIGHT_SEED`) in which both players land blows. Temp directories are removed in `finally`.

## Browser journal and menu layout

`test/rpg-quest-journal-client.test.mjs` renders `client/gameplay/quests.js` and the shell's fallback journal into a minimal DOM stand-in, using synthetic quest records only. It runs in `npm test`.

| Case | Verified behaviour |
|---|---|
| Journal states | Separate pages for no state yet (*Loading*), not in the world, and a server without the quest service (*unavailable*). A disconnected journal shows the last snapshot with a banner, and its actions are disabled. None of these say "no quests". |
| Empty journal | The page names the quest givers in the current place, nearest first. In the wilderness, a dungeon or a building it says that no one there offers work. |
| Offer and entry | Accept sends `quest.accept {offerId}`. An entry shows the giver and their place, the classic quest name, the accepted date, the running deadline (`Due by …`) and the log. Finished work shows the giver, the result and its date. |
| Privacy on one page | After leave, an account switch and a join, the recent-message feed and support report from the previous account are gone. |
| One toast | Quest events are marked `silent`, so `main.js` does not toast their text a second time. |
| Fallback | The shell's built-in journal reads the server's `{v:1, active, done}` shape instead of listing its keys. |

The live check on 2026-11-24 used the production route `/play.html` with `npm start`, a fresh registered account, the installed ARENA2, and headless Chromium over CDP. The account was created through the 10-step creator. The empty journal was checked from **J**, the menu tab, the action bar and the NPC *Open journal* link. This earlier build still had the street crier. The crier's *Any work?* gave an offer, and the Journal showed it with the giver's original text. After *Accept*, the entry and its log came from the authoritative snapshot. It was still there after a page reload, a reconnect, and a server restart on the same database. A second account (B) received none of A's quest ids or text over its socket, and B's journal showed its own empty state. Party invite and accept, and a 25-gold trade with both confirmations, ran between the two real sessions.

The menu layout audit measured every menu page at 1280×800, 853×533 (150% zoom), 740×360, 640×400 (200% zoom) and 360×640. It checked page-level horizontal scroll, menu bounds, page and tab-rail overflow, descendants that overhang the page (excluding intended nested scrollers and closed `<details>`), `elementFromPoint` sampling of what receives clicks over the menu, and whether the last control is reachable. Feature pages lay out by `@container menu-page`, the menu page's own width, not the viewport.

## Beyond the two-account test matrix

The installed-game checks for the newer exterior, dungeon, NPC and quest systems are tracked in the [classic feature backlog](classic-feature-backlog.md) and [dungeon access report](dungeon-access.md). The following limits apply to this particular test file.

- Quests: only `A0C00Y21` is played end to end here. The quest owner's tests cover `A0C00Y10` to its kill. Not exercised are quest foes killed in shared combat, prompts (`quest.answer`), `quest.use`, guild-member quests, timers expiring, refusal, one-time quests, and dungeon retrieval quests in this test file. Quest items use class descriptions where the specific classic item record is unavailable.
- Live-socket combat and magic: the live server has no test hook for spawning monsters, and reaching the authored encounters would need real-time walking. Combat and magic are verified only at the fixture layer.
- Party kill sharing (`partyKill`), party, region, and global chat channels, and moderation (mute or ban during play).
- Character level-up, guild join and training, and rest or time (`atmosphere`).
- Monsters attacking players, defeat, and revive. Monster damage happens during the fight, but the fight test refills vitals to keep the scenario stable, so these outcomes are not asserted.
- At the asset layer, only quests and travel are played. Combat, magic (SPELLS.STD) and merchants (FACTION.TXT) are verified without ARENA2. The browser checks above run separately.
